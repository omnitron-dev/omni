# Bitcoin Core public cold handoff

`xec bitcoin-cold` exports reviewed Omnitron Pipelines for registered Linux nodes. The donor remains the rollback source in its original Core format. The receiver combines its sealed online block preseed with the current cold inventory, builds a separate service-owned candidate and opens it with the official Bitcoin Core 32.1 release for offline acceptance. Publication at the service path has a separate review. The exporter and the installed Omnitron CLI can run at different revisions.

## Live observation and window inputs

Run `probe` while the reviewed unit is active. Supply `id` (a new UUIDv4), `sourceNode`, `receiverNode`, their explicit `sourceFingerprint` and `receiverFingerprint` Ed25519 SSH pins, `sourceIp`, `receiverIp`, `receiverPort`, `stageParent`, `ttlMinutes`, `sourceUnit`, `sourceCli`, `sourceConfig`, `dataDir` and `blocks`. Use the ordinary native systemd service with an explicit `-datadir` and `-conf`. The probe checks the service PID's POSIX locks on both directories, reads public RPC results, and emits the boot ID, monotonic start time, version, validated chainstates, indexes, pruning and a public height/hash checkpoint. It reports only the `-blocksdir` option from the command line. The open-file observation is supplementary to the raw-directory lock. The probe currently targets a mainnet service whose network data is directly in its declared datadir.

The cold specification has the exact fields below. `dataDir` means the network-specific directory containing `chainstate` and `blocks/index`. `blocks` means the physical directory containing the raw segments and `xor.dat`. Core allows the two directory trees to live on separate filesystems. [Core storage layout](https://github.com/bitcoin/bitcoin/blob/v32.1/doc/files.md)

| Fields | Value under review |
| --- | --- |
| `id`, `hotId`, `hotManifest` | New cold UUIDv4, original completed hot UUIDv4, exact SHA-256 of its manifest |
| `sourceNode`, `receiverNode`, `sourceFingerprint`, `receiverFingerprint`, `sourceIp`, `receiverIp`, `receiverPort`, `stageParent` | Same registered participants, direct IPv4 addresses and staging parent used by the hot preseed. The receiver port is the direct SSH listener. Both physical endpoints verify their pins. |
| `ttlMinutes`, `rateKiB` | Direct credential lifetime in minutes (1–1440) and maximum send rate in KiB/s (1–1048576). Choose a lifetime that covers the cold delta. |
| `sourceUnit`, `sourceBootId`, `sourceStartUsec`, `dataDir`, `blocks` | Verified unit such as `bitcoind.service`, boot UUID, decimal-string monotonic start from `probe`, absolute physical donor paths |
| `chain`, `anchorHeight`, `anchorHash`, `pruneMiB` | `main` or `regtest`, previously observed positive height and hex block hash, actual numeric Core prune setting (zero, manual one, or an automatic target of at least 550 MiB) |
| `indexes` | Sorted array of confirmed active optional indexes. Accepted names are `blockfilter` (basic), `coinstatsindex`, `txindex`, `txospenderindex`. An empty array requires absence of on-disk optional indexes. The mandatory block index always transfers. |
| `candidateParent`, `targetUser`, `targetUid`, `targetGid` | Root-controlled receiving parent with room for an independent candidate, and service account with confirmed nonzero numeric Linux IDs |

Require one validated source chainstate. Parallel AssumeUTXO trees, stale optional indexes, unrecognized LevelDB entries, missing locks and missing or malformed XOR material stop the operation. Retain the donor, its effective configuration and the unmodified 31.x deployment through the rollback window.

## Operator sequence

Export a graph to a local JSON file and run the ordinary review/start sequence for each phase. Review participants, graphs and receipts before advancing. `offer.json` is the public JSON object from the successful cold source `offer` step.

```sh
pnpm exec xec bitcoin-cold probe probe.json > probe-pipeline.json
omnitron --json pipeline check probe-pipeline.json
omnitron --json pipeline save probe-pipeline.json
omnitron --json pipeline run <definition-id> --run-id <new-run-uuid> --prepare
omnitron --json pipeline start <run-id> --expected-digest <review-digest>
omnitron --json pipeline status <run-id> --output
```

1. Complete and seal `xec block-preseed` on the original registered nodes. Save the verified hot UUID and digest. Obtain the agreed clean shutdown of the source in its own service lifecycle. The cold graphs only inspect the systemd exit and hold shared POSIX locks on the existing data, raw-file and LevelDB lock inodes. Offer and send both check the same boot and exact invocation before and after reading. If systemd has discarded the exit record or the donor has restarted, collect a fresh live probe and arrange a clean stop for a newly reviewed operation.
2. Export `pnpm exec xec bitcoin-cold offer cold.json`. The receiver first confirms its original hot seal and physical stage identity. The donor then enumerates every remaining `blkNNNNN.dat` and `revNNNNN.dat`, including the current tail and pruning gaps, the exact eight bytes of `xor.dat`, current LevelDB tables, numeric WALs, CURRENT and manifests from the block index, chainstate and declared optional indexes. It checks each nonempty segment's first frame against the reviewed network magic, length and existing XOR material, then hashes the retained donor bytes at nice 19 and best-effort I/O priority 7 when available. This full read accounts for the absence of source inode receipts in the original hot protocol. Rows which pruning has removed disappear from the cold manifest. Source inode identity and modification metadata are rechecked before streaming.
3. Export `pnpm exec xec bitcoin-cold copy cold.json --offer offer.json`. Every digest-identical closed hot file is referenced in place on the receiver. The remaining files cross directly via source-IP-bound, short-lived, forced SSH under a non-root account. The receiver writes only manifest-approved numbered regular files in its operation stage. The seal rehashes both independent input sets, revokes the receiver and forgets the donor key.
4. Export `pnpm exec xec bitcoin-cold adopt cold.json --offer offer.json`. The receiver creates `candidateParent/bitcoin-<id>/data`, verifies the service account and makes a distinct inode for each file. It uses FICLONE on supported filesystems and otherwise copies verified bytes locally. The fallback can require space for a complete second target copy. Native processes cannot see an incomplete candidate. The retained root-owned hot and cold seals continue to contain the pre-upgrade inputs.
5. Export `pnpm exec xec bitcoin-cold qualify cold.json --offer offer.json --release release.json`. For installed x86_64 binaries use `{"machine":"x86_64","binDir":"/opt/omnitron/binaries/bitcoin-core/32.1"}`. The receiver checks both executables against independent SHA-256 pins derived from the signed release. For x86_64 or aarch64 an alternative input uses `archive` with the absolute on-host official archive path and its `machine`. The receiver checks the pinned 32.1 release, opens the new candidate as the service UID in a network namespace with loopback alone, disables wallet and peer activity, uses private temporary local authentication and checks version, chain, descendant checkpoint, pruning target, validated tip, optional index synchronization and native `verifychain 3` to an available depth of at most 288. Before opening the database, it checks the adopted data-directory inode and the allowed on-disk layout. Qualification closes once a publication intent exists. It closes Core cleanly and records the accepted tip and physical inventory. A pruned copy provides the history still retained by its donor. [Bitcoin Core 32.1 release](https://bitcoincore.org/en/releases/32.1/)
6. After separate publication approval, export `pnpm exec xec bitcoin-cold publish cold.json --offer offer.json --installation install.json`. This binds the canonical directory on the same receiving filesystem and checks that the target service is inactive. An example installation input is `{"unit":"bitcoind.service","dataDir":"/var/lib/bitcoind","previous":{"kind":"absent"}}`. An existing empty directory requires `{"kind":"empty","device":"…","inode":"…"}` using observed decimal strings from `stat -c '%d %i'`. Populated or substituted destinations are refused. Atomic Linux rename or exchange and durable physical identities support reconciliation after a lost acknowledgement. Service start and private identity provisioning belong to their separate operator plans.
7. To restore the pre-publication target after a separately approved clean stop, export `pnpm exec xec bitcoin-cold restore cold.json --offer offer.json --installation install.json`. The operation revalidates its paths, moves its public candidate back and restores the previous absent path or exact empty inode. Private material added after publication requires separate handling before a public-tree handoff. A published candidate may have undergone a format change. For a 31.x fallback use the original donor with its pre-upgrade binary and tree. Never open a 32.1-upgraded txindex with the older binary. Core 32.1 reads an existing 31.x txindex. An explicitly rebuilt 32.1 txindex uses a smaller format that earlier releases cannot read directly. [Core 32.1 database changes](https://bitcoincore.org/en/releases/32.1/)

The donor selects public chain filenames explicitly. Wallets, cookie and RPC credentials, onion keys, mempool, configuration and diagnostic logs never enter the transfer manifest. A terminal controller error after sending can leave a physical SSH session running. Reconcile both operation locks, the sender receipt and the sealed stage before retrying. With both sides idle use `accept cold.json --offer offer.json` for an already completed stream, or replay `copy` for incomplete work. The receiver verifies retained complete objects and retries only the missing delta. For an expired grant, run `revoke cold.json`, then obtain a fresh offer for the same exact cold inventory. Repeated publication and restoration reconcile the two recorded physical directory identities.

The source and receiver require Linux, Python 3.9+, OpenSSH, root management, the native Bitcoin files, and a root-controlled stage. Target publication uses Linux `renameat2`. Offline qualification requires permission to create an isolated network namespace or an existing namespace containing only loopback. The exported shell steps keep each cold management command below 22 KiB. The content-addressed helper installer performs host-pin and digest checks on each bounded chunk. Older daemons can check and execute the exported graphs through their ordinary Pipelines API.

Run `python3 -B .xec/bitcoin-cold/scope_test.py` and `node --test .xec/bitcoin-cold/export.test.js`. The opt-in `stand_test.py --help` describes a two-host disposable Linux fixture using actual signed 31.1/32.1 executables, protocol-valid regtest blocks, authenticated node-to-node SSH, the installed native Pipeline checker and a real old-format rollback source.
