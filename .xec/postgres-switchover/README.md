# Physical PostgreSQL switchover

Use this Pipeline when the receiving site gets the application PostgreSQL 17 and Nominatim PostgreSQL 14 clusters through native physical replication. It verifies a base backup, witnesses the old primary's final WAL on the standby, and can promote two private candidates. The existing service-data Pipeline handles flatnode, merged, Redis and MinIO independently. A site admits a new writer only after both database receipts, the four restored volumes, the Nominatim import generation and its other ownership gates have passed. [Four-volume acceptance](../service-data-adopt/README.md#file-acceptance-with-two-physical-postgresql-replicas)

## Access and online preparation

Use the previously reviewed six-volume specification with the two PostgreSQL system identifiers. Confirm matching architecture, PostgreSQL major and on-disk build parameters at both sites. This physical path supports both clusters with internal WAL and no external tablespaces. The original full cold transfer remains available for other layouts.

1. Obtain separate local approvals for the donor's physical replication login and the receiver's private channel. For each source cluster use a dedicated, expiring `LOGIN REPLICATION` role with no superuser, role/database creation, bypass-RLS or inherited memberships. Admit the `replication` pseudo-database from the exact private endpoint with SCRAM. Restrict ordinary database logins for this role. Keep the replication password or client credential in an owner-only passfile on the receiver. A physical replication login can read the entire cluster and manage replication slots. Scope its credential to the reviewed receiver and check the donor slot inventory during the transfer. [PostgreSQL replication authentication](https://www.postgresql.org/docs/17/warm-standby.html#STREAMING-REPLICATION-AUTHENTICATION)
2. Approve a direct source-to-receiver data path with the registered SSH host pins, an expiry, and access to just the selected replication endpoint. A reviewed private Unix socket on the receiver can terminate the encrypted link. Bind the server-side relay to a distinct private address so its first matching HBA records allow physical replication only for that role and reject general database and other replication logins. Test the effective restrictions before issuing its credential. Do not expose a public PostgreSQL listener, enable generic SSH forwarding, include passwords in a graph, or reuse the file-stage rsync key. Size the lease for the full base transfer, receiver verification and WAL catch-up, or renew it under separate approval before expiry. Password expiry affects new authentication. Revoke the durable admission and terminate its existing sessions on completion. On PostgreSQL 14, a database superuser must create the replication role. PostgreSQL 17 also allows an issuer with both CREATEROLE and REPLICATION. The source owner separately approves and reloads the HBA rules. The client itself uses only the dedicated physical replication login. [PostgreSQL 14 role creation](https://www.postgresql.org/docs/14/sql-createrole.html) · [PostgreSQL 17 role creation](https://www.postgresql.org/docs/17/sql-createrole.html)
3. Measure free space on the real receiver **Docker volume filesystem**, source WAL filesystem and any separate WAL spool. Budget for both native backups, WAL during transfer and offline verification, four independently decoded data volumes, and the site's disk reserve. Account for both transfers sharing the rate cap. For a single transfer of `N` logical bytes at `R` KiB/s, `N/(1024R)` is a transfer-time lower bound at that cap. Measure the WAL rate over a representative interval. Native backup verification reads each receiving cluster once. A warm rsync logical-byte count after a resume does not measure network throughput.
4. Run the matching image's `pg_basebackup` directly into each new, empty and disjoint rootless named volume. A private physical data path supplied by the receiving site can be used as follows. Set `PGHOST`, `PGPORT`, `PGUSER` and `PGPASSFILE` inside the isolated holder to its reviewed endpoint, role and protected credential. Keep its owner-only passfile inside the single reviewed read-only channel directory mounted at `/run/omnitron-source`. Use the same absolute passfile path in the standby connection settings so reconnections work throughout verification. Verify the source system identifier with physical `IDENTIFY_SYSTEM` first. Serial transfers can use the full approved base-backup rate. Concurrent transfers must divide that budget and allow for WAL traffic.

```sh
pg_basebackup --pgdata="$PGDATA" --format=plain --wal-method=stream --no-slot \
  --manifest-checksums=SHA256 --write-recovery-conf --no-password --no-clean \
  --max-rate="$BASE_RATE_KIB"
```

Each source needs `wal_level=replica` or `logical` and enough `max_wal_senders` for two connections during its streaming base backup and one for a connected standby. Each receiver needs `hot_standby=on` for the private SQL checks. The operation creates no permanent or temporary replication slot. `--no-clean` leaves an interrupted destination for inspection. Start again in another fresh volume only after a separate decision. When the source cannot retain enough WAL through the transfer and full verification, start a bounded, receiver-side `pg_receivewal` archive beforehand through the same authenticated route and make completed segments available to standby recovery. Budget the extra WAL sender and spool disk space. Require uninterrupted WAL coverage through the base and terminal position. An unavailable required segment blocks promotion. [PostgreSQL 17 base backup](https://www.postgresql.org/docs/17/app-pgbasebackup.html) · [PostgreSQL 14 base backup](https://www.postgresql.org/docs/14/app-pgbasebackup.html) · [Native WAL receiver](https://www.postgresql.org/docs/17/app-pgreceivewal.html)

## Receiver binding and ordinary Pipeline stages

Each receiver holder runs the exact source OCI image by immutable ID under the independently admitted rootless Docker engine. Create its server container with native `postgres` as the entrypoint and keep it stopped through base verification. Set its label `omnitron.pg-switchover` to the service specification's `id`. Attach only the new named PGDATA at the original container path and the reviewed, read-only private source channel at `/run/omnitron-source` if required. Reserve a separate private local volume named `omnitron-pg-socket-<seed>-<major>` at `/run/omnitron-pg`, owned by the mapped PostgreSQL UID with mode 0700. Set `volume-nocopy` on these mounts so image defaults cannot replace the ownership of an empty reserved volume. Native observer containers attach this socket volume and PGDATA read-only. Ephemeral tmpfs mounts can cover unused image-declared mounts. Use `--network none`, a read-only root filesystem, dropped capabilities, no-new-privileges, no published ports, a private PID namespace and restart policy `no`. No other container may be attached to the candidate volume. Keep the holder and its PGDATA inode across all stages. The receiving site must hold deployment admission so ordinary apps cannot attach while the candidates are private.

The binding records physical inode numbers as strings. Supply the target engine UID and the exact container IDs, fresh volume names and receiver device/inode observations for each cluster.

```json
{
  "schema": 1,
  "seed": "<service specification UUID>",
  "engineUid": 995,
  "candidates": {
    "postgres": { "container": "<64 hex>", "volume": "<PG17 volume>", "device": "<decimal>", "inode": "<decimal>", "socketDevice": "<decimal>", "socketInode": "<decimal>" },
    "nominatim": { "container": "<64 hex>", "volume": "<PG14 volume>", "device": "<decimal>", "inode": "<decimal>", "socketDevice": "<decimal>", "socketInode": "<decimal>" }
  }
}
```

When the rootless engine requires a named AppArmor profile, add `"apparmor": {"name": "omnitron-…", "sha256": "<64 hex>"}` to the binding. The site separately approves and installs the enforcing profile for both the private server and its native observers. The worker verifies the root-owned policy file, digest, enforcement and explicit container option. On a running holder it reads the effective kernel label through the actual postmaster PID and matches both mounted inodes through that process. Observers use new, short-lived containers with read-only mounts.

Each command exports a normal manual Omnitron Pipeline definition. Use the installed project's `pipeline check`, reviewed execution and `pipeline status --output` for that definition. Use the same exporter revision and Node runtime for the four graphs. Prerequisite files contain ordinary successful status responses keyed by stage. Later graphs look them up on the controller and compare node identities, reviewed commands, outputs and review digests.

```sh
xec postgres-switchover base spec.json --binding receiver.json
xec postgres-switchover source spec.json --binding receiver.json --stop "$FULL_STOP"
xec postgres-switchover replay spec.json --binding receiver.json --stop "$FULL_STOP" --evidence base-source.json
xec postgres-switchover promote spec.json --binding receiver.json --stop "$FULL_STOP" --evidence base-source-replay.json
```

- **base** runs `pg_verifybackup` on both offline backups, checks per-file SHA-256 and the WAL ranges, pins the verified manifest digest, physical volume, image, container and native system identifier. After success start those two created containers as standbys. Supply the source's necessary recovery settings including limits and Nominatim's external PostgreSQL configuration. Set `listen_addresses=''`, `unix_socket_directories='/run/omnitron-pg'`, port 5432 and a local HBA admitting the trusted in-holder `postgres` OS user for SQL and physical identity queries. Set `default_transaction_read_only=on`, `max_logical_replication_workers=0`, `archive_mode=off`, empty shared/session/local preload libraries, and empty `archive_cleanup_command` and `recovery_end_command`. A private promoted instance could otherwise execute subscription changes or extension jobs without a client. The witness checks these server settings and active backend types through the private socket. A primary session can override the read-only default, so the site retains exclusive control of that socket and deployment authority. The local administrative identity is separate from the donor's replication role. Allow the restored candidate to finish its initial durable synchronization and open for read-only SQL while the source is serving. Before scheduling the stop, record a site-native observation on each candidate. Require one streaming WAL receiver, a null receiver slot, an empty configured primary slot, the expected source timeline, and enabled fsync and full-page writes. Have the separately authorized source operator or PostgreSQL monitor check the donor's matching sender and slot inventory. The dedicated physical login can remain restricted to the replication protocol. Retain those online observations with its private-channel review.

  ```sql
  SELECT status, slot_name, received_tli, flushed_lsn, latest_end_lsn
    FROM pg_stat_wal_receiver;
  SELECT current_setting('primary_slot_name'), current_setting('fsync'),
         current_setting('full_page_writes');
  ```
- **source** requires the controller's current full stop, both old primaries' clean shutdown, zero writable container attachments, both original PGDATA inodes and a persistent kernel writer fence on each root. The site takes that fence under its own approved custody. After a successful full stop, verify exact device/inode, PostgreSQL identity, clean control state and the absence of `postmaster.pid`. On a supported Linux filesystem the privileged site owner can set `FS_IMMUTABLE_FL` on that specific directory inode. Read it back, confirm the PID file is still absent and hold exclusive authority over removing this flag. The immutable directory prevents a new PostgreSQL postmaster from creating its required lock file through the named volume or any bind alias. The Pipeline only observes this interlock. Read the native control checkpoint and exactly one WAL record at that position using the pinned image's `pg_waldump`. It must identify `CHECKPOINT_SHUTDOWN` with the same timeline and starting LSN. The source receipt also records the fenced Nominatim `import-finished` content digest, byte count and source modification time.
- **replay** verifies that each private candidate is still in recovery and uses native physical `IDENTIFY_SYSTEM` to read its replay position and timeline together. The identifier and timeline must match the source. The replay LSN must be **strictly greater** than the terminal record's starting LSN. A pre-stop flush LSN can equal that start even while the record has not been replayed. The source fence is observed again before and after the receiver step. The manifest check in this and subsequent stages reads only the manifest. Nominatim's private marker must match its fenced source content. Successive imports can touch the same empty marker without changing its digest. Before site write admission, reconcile the source marker's recorded time and content with the stopped flatnode, merged output and the receiver's import generation. A missing or changed marker blocks the private witness as well.
- **promote** prechecks both candidates, promotes them inside their isolated holders with native `pg_promote(true,45)` over the private Unix socket, and reads the new system identifier, timeline and native history file. The final history entry must fork directly from the witnessed timeline at or after its replay LSN. The old site remains fenced. Partial promotion or a lost reply can be reconciled under the same accepted replay by checking the existing child timeline. Both candidates remain private between attempts. After obtaining the final registered Pipeline status, put all four successful status responses in `all-runs.json`. Collect the typed PostgreSQL receipt with `xec postgres-switchover receipt spec.json --binding receiver.json --stop "$FULL_STOP" --evidence all-runs.json`. This local command rereads all four referenced runs from the registered controller and compares their reviews, step identities and exact output digests before joining the site records. It requires controller read access. Backup, promotion and file checksums run only in their respective Pipelines. Preserve the referenced controller records and their review digests as the authoritative observations. The combined receipt reports `privately-promoted`. [Physical protocol and `IDENTIFY_SYSTEM`](https://www.postgresql.org/docs/17/protocol-replication.html) · [PostgreSQL backup integrity](https://www.postgresql.org/docs/17/app-pgverifybackup.html)

## Write admission and recovery

Keep both original volumes and the old writer fences under site custody. Complete the four-volume receipt, independently reconcile the stopped Nominatim import generation, and accept the two native PostgreSQL witnesses. The site must record a durable, exclusive writer decision **before** publishing any route or granting application access to either new primary. After a successful gate, deploy with the exact reviewed candidate volume identities. Keep the old PostgreSQL data fenced for as long as the new site owns the writes.

Promotion writes a new PostgreSQL timeline and its own WAL. Before admitting any authoritative application work, the site can abandon the candidates, even after private promotion. Durably withdraw their deployment and routing admission first, stop both real postmasters, close and attest both receiver PGDATA fences, and record their volume identities and absence of authority to admit writers. Only then may the source owner release its original inode fences and restore the old stack. Keep a terminal abandonment decision so an earlier receiver review cannot subsequently admit the same candidates. A completed stack stop alone permits an explicit new deploy. SQL row counts, a missing client at inspection time, a changed timeline or a lost reply cannot establish that the target never admitted authoritative writes.

After target write admission, including an ambiguous published outcome, the old primary needs controlled reverse synchronization before it can serve. `pg_rewind` requires data checksums or enabled `wal_log_hints` on its target before the timelines diverged, full-page writes and the necessary WAL. A deployment with both settings off requires a fresh reverse physical base after divergent writes. The operator must reconcile ownership before restoring either side. [PostgreSQL 17 rewind requirements](https://www.postgresql.org/docs/17/app-pgrewind.html) · [PostgreSQL 14 standby and failover](https://www.postgresql.org/docs/14/warm-standby.html)
