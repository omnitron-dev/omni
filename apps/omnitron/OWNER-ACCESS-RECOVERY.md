# Recovering application access as the installation owner

**Proposed v1 contract.** One human who enrolled recovery credentials before losing access can replace the password of their paired account in a participating application. The controller verifies the owner. The application alone receives the new password, changes the account and attests to the outcome. The names below describe proposed interfaces. Omnitron 0.4.16 exposes no such recovery service.

## What the platform already guarantees

| Boundary audited at `fe3ca3e7` | Existing guarantee | Work required for recovery |
| --- | --- | --- |
| [Daemon invocation](src/services/daemon-authority.ts) and [Titan session authority](../../packages/titan-auth/src/preset/session-authority.ts) | Human calls can be checked against a live session. Service and local administrator principals have distinct admission rules. The ordinary [password change](src/services/auth.rpc-service.ts) checks the current password. | Identify the pre-enrolled installation owner even after loss of application access. A role or a local socket cannot establish this identity. |
| [Mesh enrollment](src/cluster/enrollment.ts) and [stack effect authorization](src/cluster/stop-authority.ts) | A recipient can verify an audience, a signed effect and its leadership term. | Bind a human-approved credential operation to one application, subject and revision. Give recovery its own method and signing domain. |
| [Operation journal](src/execution/operation-journal.ts) and [installed application resume](src/project/installed-stack-resume.ts) | Operation IDs, input digests and revision checks survive restart. Resume can query the recipient for a missing reply and match it to the original plan. | Admit proof, spend a code and record approval together. The journal's execution-resource observation cannot attest to an account transaction. |
| [Operator account provisioning](src/services/project.service.ts) and [transactional replication receipts](src/services/replication-reconciliation.ts) | Provisioning invokes an application and then saves a generated secret in the controller vault. Replication already has a pattern for recording a result alongside the affected data. | Implement the latter pattern in the application's credential store. A gap between an application commit and a vault write, or a missing account in a later query, cannot establish the outcome of an individual attempt. |

Here “owner” means the enrolled human. Omnitron's [resident process owner](src/daemon/owner-reconciliation.ts) supervises processes and has a separate identity and recovery lifecycle.

## Enrollment and scope

Provision one immutable installation ID and a commissioning trust anchor before exposing enrollment. Commissioning requires the existing anchor to authorize the owner ceremony. Pin one opaque owner ID, a user-verifying WebAuthn credential and a generation number in a single conditional write. The owner verifies possession at enrollment and stores a set of independently generated, single-use 128-bit recovery codes offline. Keep only salted verifiers, enforce durable rate limits and issue replacement codes in an authenticated owner ceremony. The code and authenticator should be kept separately. [WebAuthn assertion verification](https://www.w3.org/TR/webauthn-2/#sctn-verifying-assertion) · [NIST guidance on saved recovery codes](https://pages.nist.gov/800-63-4/sp800-63b.html#savedrecovery)

While the owner still has access to the application, require fresh authentication as the application subject and proof of the installation owner in the same pairing ceremony. Pin the installation, application recipient and verification key, exact web origin, immutable application subject and supported method together. Enforce uniqueness for the installation owner and for this pairing. Names, roles, hostnames and app display labels can change. They do not select the account. An existing installation without verifiable commissioning authority cannot enable recovery through this protocol. Loss of both the enrollment path and a required factor leaves recovery unavailable.

The controller binds each intent to the protocol major version, installation and owner IDs, owner generation, application recipient and pairing generation, immutable subject, credential revision, exact method, operation UUID, application browser-session binding, issue time and absolute expiry. Use SHA-256 over domain-separated canonical JSON with a strict versioned schema and integer timestamps. Reject duplicate, missing, unknown or ill-typed input fields. Both parties compute the digest. A repeated UUID with a different digest is a conflict. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)

## One recovery through the normal entry points

| Step | Caller and interface | Durable decision |
| --- | --- | --- |
| 1. Open recovery | The owner opens the enrolled application origin. Its backend calls the proposed `OmnitronOwnerRecovery@1.begin` over authenticated Netron. | The application creates a private, expiring browser session. The controller verifies the registered recipient, generates a fresh challenge bound to the intent digest and fixes a five-minute deadline. A challenge does not reserve the subject indefinitely. |
| 2. Confirm the operation | On the controller's enrolled HTTPS origin the owner reviews the installation, application, account and action, verifies with the enrolled authenticator and submits one offline code to `approve`. | Verify the RP ID, exact origin, fresh challenge, signature and user presence/verification. Compare the current enrollment generations. In one transaction consume the challenge and code, acquire the subject lock, record the approved digest and audit the decision. Failed admission cannot spend a code or leave a partial approval. |
| 3. Return to the application | The controller releases a short-lived, single-use continuation only to the browser that completed the proof. The application accepts it on its enrolled origin and checks the original private browser session and anti-CSRF binding. | Bind both halves of the return to the same intent. For example, use a form POST to an exact pre-registered HTTPS callback with a separate same-browser session check. A URL, public status response or operation UUID must never provide a usable continuation. |
| 4. Claim and apply | The owner submits the new password directly to the application. Its backend uses the continuation to call `claim` as the enrolled recipient. The application dispatches its fixed `ApplicationOwnerRecovery@1.replaceOwnPassword` handler. | Claim compares the approved digest, audience, generations and deadline under a controller transaction. Return a domain-separated, recipient-verifiable grant for this one claim. The application verifies it, locks the operation and subject, checks expiry and expected credential revision at the mutation boundary, then writes the password verifier, advances the session revocation epoch and stores the applied receipt in one transaction. |
| 5. Read the outcome | The application returns an authenticated receipt. After a lost response the controller reads `ApplicationOwnerRecovery@1.receipt` on the enrolled recipient. The owner signs in normally. | Match version, installation, recipient, pairing generation, subject, UUID, digest, outcome and resulting revision. A matching applied receipt answers a replay without a second change. A mismatched receipt leaves the operation unresolved and raises an incident. |

The two service names denote a closed set of typed methods. Discovery is opt-in and negotiates a supported major version. An arbitrary Netron method name, callback URL, shell or agent tool cannot be supplied by the requester. Keep the owner approval surface on the controller and the password form on the application origin. Browser responses use `no-store` and a restrictive referrer policy. Keep passwords, verifiers, offline codes, assertions, continuations, signed grants and raw request bodies out of general-purpose logs, traces, operation journals and analytics. Store verifiers only in their dedicated authoritative stores. Audit by opaque IDs, generations, timestamps, decisions and receipt digests. Access to audit/status is restricted; anonymous responses must not identify enrolled subjects.

## Cancellation, concurrency and recovery

The controller serializes approval, claim and cancellation for one installation and application subject. The application serializes mutation and fencing for the same operation and subject across its replicas. Each needs a single authoritative writer or equivalent transactional consistency. A partition that prevents a required check suspends progress.

Expose controller `status` and `cancel` only to the enrolled owner with current proof or the recipient authenticated for this operation. A cancellation changes only the named operation. Application `receipt` and `fence` accept the paired recovery authority and exact intent. Status never returns a proof or a grant. If a claim response or browser session is lost before delivery, consult the receipt and fence an abandoned claim. Restarting either process cannot reissue authority from an operation ID alone.

| Last durable fact | Cancellation, expiry or lost response |
| --- | --- |
| Pending or approved, unclaimed | Cancellation and expiry can close the operation on the controller. A simultaneous claim must lose if closure committed first. An approved operation's code stays spent. Releasing the subject lock permits a new attempt with fresh proof. |
| Claimed, no conclusive application receipt | Record the outcome as unknown and retain the lock. Read the receipt. To establish non-application, request a fence at the recipient. A missing row, timeout or an elapsed deadline is insufficient. |
| Application receives a fence | In the same serialization domain as password replacement, return the committed receipt if one exists. Otherwise write a durable no-effect receipt for this UUID and digest. A late apply must observe that fence. |
| Applied or fenced receipt verified | Store the result before releasing the lock. Matching retries return that result. Loss of a callback or controller restart permits another receipt lookup. A new password submission requires a new authorized attempt once the previous outcome is known. |

Use the current application session authority on every privileged call so the credential revision invalidates existing cookies, refresh tokens and long-lived connections. Abort the credential transaction if the application cannot make revocation effective through its normal authentication path. Recovery grants no additional roles, changes no authenticator bindings and yields no logged-in session.

Rotation or transfer increments the authority generation and invalidates unclaimed approvals. Drain or fence claimed operations at every affected recipient before declaring rotation complete. On failover or backup restore, establish the current generation and single writer against a trusted monotonic record outside the restored snapshot before accepting recovery traffic. If currency cannot be proved, require recommissioning through the independent trust anchor and fence the old writer and grants first. Retain terminal receipt identities and spent-code evidence for every generation still accepted. A restored snapshot must never revive a spent code, removed enrollment or fenced grant. The design assumes trusted controller and application hosts, authenticated transport, bounded clock uncertainty and durable transactions. Local host compromise is outside these guarantees.

## Acceptance before exposing the capability

The [bounded execution model](test/unit/owner-recovery-model.test.ts) checks the race between claim, cancellation, expiry and an application commit whose acknowledgement was lost. It represents transactions as atomic steps. It does not exercise WebAuthn, Netron, browser origin handling, database isolation or backup recovery.

| Gate | Evidence required through product entry points |
| --- | --- |
| Commissioning and proof | An unenrolled installation, an ordinary administrator, a service principal, a single factor, stale generations, wrong origins and reused challenges all fail. Two simultaneous proofs using the same code permit one approval. Rate limiting survives reconnection and restart. |
| Browser and scope | Two isolated browser profiles and two application origins cannot exchange continuations or change the operation's subject or method. A valid owner can complete recovery after losing the application session. Verify redaction at both HTTP/RPC ingress points and in stored telemetry. |
| Atomicity and cancellation | With two application replicas, race claim, cancellation, expiry, rotation and apply. Drop the connection before and after each commit. Check the application credential revision, revocation epoch, controller code usage and exact receipt. Include a late commit after an empty receipt lookup. |
| Mesh, failover and restore | Refuse a wrong recipient and an unsupported version. Reconcile across controller restart, app replica replacement, a split mesh and independent database restores. Verify that historical operation IDs, grants and codes cannot acquire new authority. |
| Ordinary user path | Exercise the application form, real WebAuthn assertion, old and new password sign-in, outstanding sessions and a long-lived connection on a second replica. Require a matching receipt for the enrollment's subject before presenting completion. |

Implementation order is commissioning and pairing, controller admission and receipts, one opt-in application adapter with transaction and revocation support, then the two browser surfaces. Enable recovery per installation only after the complete path satisfies these gates.
